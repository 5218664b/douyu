# douyu-streamer

这是一个面向树莓派 4B 的斗鱼自动推流系统设计文档。

新系统不再沿用当前仓库中 Python、Node.js、shell、浏览器自动化和本地 relay 混合在一起的实现方式，而是收缩为一条更短、更稳、更轻的主链路：`Go 主程序 + ffmpeg 直推斗鱼`。

本文档只描述重构后的目标架构，不描述旧脚本如何运行。

## 建议使用方式

宿主机日常开发调试，优先从统一入口进入：

```bash
./scripts/dev/menu.sh
```

这个入口会用中文菜单提供完整的宿主机调试与发布功能：

- 一键扫码并启动树莓派推流
- 仅更新并重启树莓派 app
- 仅更新并重启树莓派 relay
- 仅更新并重启树莓派 scan-provider
- 发布 app 镜像到树莓派
- 发布 relay 镜像到树莓派
- 发布 scan-provider 镜像到树莓派
- 发布 app/relay/scan 全部镜像到树莓派

如果你已经熟悉各脚本，再直接使用 `scripts/dev/` 或 `scripts/pi/` 下的细分脚本即可。

## 设计目标

新系统围绕以下原则设计：

- 树莓派优先：以 Raspberry Pi 4B 的 CPU、内存、IO 和长期运行稳定性为首要约束。
- 主链路最短：播放器调度与推流尽量直连，减少中间服务和故障点。
- 低服务复杂度：默认不引入 relay、浏览器自动化取码、数据库和多服务编排。
- Docker 优先：为了和树莓派上其他应用的部署方式统一，主系统默认以单容器形式交付。
- 可扩展：弹幕控制、状态接口和外部辅助工具保留扩展边界，但不进入第一层核心链路。

## 系统概览

重构后的系统只保留两个核心运行单元：

- `app`：Go 主程序。负责配置加载、视频扫描、播放队列、视频切换、弹幕控制、状态管理和本地 API。
- `ffmpeg`：由主程序在容器内托管的推流子进程。负责把当前视频推送到斗鱼远端 RTMP 地址。

系统主链路如下：

1. `app` 从挂载的视频目录扫描可播放媒体文件。
2. `app` 根据顺序策略建立播放队列。
3. `app` 启动 `ffmpeg`，将当前媒体直接推送到斗鱼。
4. `app` 维护当前项、下一项和播放历史，并在合适时机触发切换。
5. `app` 监听斗鱼弹幕，把控制命令转换为播放队列变更。
6. `app` 通过本地 HTTP API 输出状态信息，供查看和运维使用。

默认情况下，系统不依赖本地 relay，不依赖常驻浏览器自动化取码，也不依赖数据库。

## 主程序架构

主程序建议使用 Go 实现，并作为系统唯一主进程运行。

选择 Go 的原因很明确：

- 单二进制适合做轻量容器镜像
- 长时间运行稳定
- 并发处理弹幕、状态和进程管理更直接
- 比 Python + Node.js 混合栈更适合树莓派长期运行

主程序内部模块如下：

- `config`：读取 `app.yaml` 和环境变量，输出统一配置对象。
- `library`：扫描视频目录，识别可播放文件并提取基础元数据。
- `playlist`：维护播放队列、当前项、下一项和历史记录。
- `stream`：托管 `ffmpeg` 进程，负责启动、停止、重启和异常处理。
- `danmaku`：连接斗鱼弹幕源，解析消息并转化为控制命令。
- `state`：维护当前运行状态、当前视频、推流状态和错误信息。
- `api`：提供本地 HTTP 接口，用于读取状态和触发有限控制操作。

## 推流模型

新系统的核心推流策略是：`ffmpeg` 直推斗鱼。

这意味着：

- 不在第一版中引入本地 `nginx-rtmp`
- 不做“主程序 -> relay -> 斗鱼”的双层推流
- 不用 relay 的 `/stat` 接口作为切换决策基础

直推方案的优先级更高，是因为树莓派 4B 更需要降低运行复杂度，而不是追求过早的平滑切换优化。

主程序只负责：

- 准备当前推流媒体
- 生成 `ffmpeg` 启动参数
- 启动或切换推流进程
- 监控进程退出状态
- 在错误时进行有限恢复

## 媒体策略

树莓派 4B 的主线方案默认假设：素材应尽量预处理成适合推流的统一格式。

推荐策略如下：

- 视频库提前整理
- 尽量统一容器格式
- 尽量统一编码参数
- 推流时优先使用 `copy` 或低负载处理方式

原因是树莓派 4B 的长期稳定性高度依赖 CPU 和 IO 压力可控。相比运行时实时转码，预处理素材更符合这个目标。

因此系统默认支持两类文件策略：

- 推荐模式：预处理后的统一推流素材
- 兼容模式：直接读取原始 `.mp4` 文件，在必要时由 `ffmpeg` 做适配处理

推荐模式是主线，兼容模式是补充。

## 播放与切换模型

播放队列是显式模型，不再依赖 shell 休眠、软链接切换或临时 concat 文件拼接逻辑。

每个媒体项至少包含：

- 唯一 ID
- 文件路径
- 展示名称
- 媒体格式
- 时长
- 当前顺序位置

播放队列支持以下能力：

- 初始化扫描目录生成队列
- 顺序播放
- 重新加载视频库
- 调整下一项优先级
- 记录最近播放历史

切换策略由主程序控制，不依赖额外中转层的状态接口。系统优先保证：

- 播放顺序清晰
- 切换逻辑可控
- 异常时可恢复

第一阶段不以“完全无缝切换”作为架构前提，而以“稳定可重复运行”作为首要目标。

## 弹幕控制模型

弹幕接入被视为播放控制输入源，而不是主业务核心。

弹幕模块只负责：

- 连接斗鱼弹幕源
- 解析消息
- 识别符合约定的控制命令
- 将命令交给播放队列模块处理

推荐保留的命令集很小：

- `#3`：将目标项提升到下一轮
- `#next`：切换到下一项
- `#reload`：重新加载媒体库

这样设计是为了降低树莓派上的运行复杂度，同时保留项目原本最有价值的互动能力。

## 推流码策略

自动获取推流码不属于主系统。

主系统默认只接受以下输入：

- `remote_rtmp_url`
- `remote_stream_key`

这两个值通过配置文件或环境变量提供。

自动获取推流码如有需要，应当作为独立辅助工具存在，并且建议在桌面环境中执行，而不是作为树莓派上的常驻能力。原因如下：

- 浏览器自动化资源占用高
- 页面结构变动频繁
- 失败率高于主链路
- 不值得拖累树莓派主系统稳定性

因此，树莓派 4B 主线架构不包含常驻取码服务。

## API 与状态模型

新系统默认提供本地 HTTP API，用于状态读取和少量控制操作。

API 目标包括：

- 查询当前运行状态
- 查询当前播放项
- 查询播放队列
- 查询最近错误
- 触发重新扫描媒体库
- 触发切换下一项

状态机建议保持明确，至少包含：

- `idle`
- `preparing`
- `streaming`
- `switching`
- `recovering`
- `error`

主程序应持续输出结构化日志和可观测状态，而不是依赖 shell 输出拼接运维信息。

## 运行模型

树莓派 4B 上的推荐运行方式是：

- 主程序编译为单二进制
- `ffmpeg` 打包进同一个应用容器
- 使用单容器 Docker 运行主系统
- 视频目录通过 volume 挂载
- 配置文件通过 volume 或环境变量注入

默认不要求：

- 多容器编排
- 浏览器运行时
- 数据库存储
- 本地 relay 服务

如果后续需要和其他服务一起统一管理，可以使用 `docker compose`，但主系统仍保持单应用容器，不拆成多服务主链路。

## 树莓派硬件假设

本文档默认部署环境为 Raspberry Pi 4B。

建议的硬件与运行前提如下：

- 建议 4GB 内存及以上
- 建议使用外接 SSD 而不是仅依赖低质量 SD 卡
- 建议有主动散热
- 建议使用稳定电源
- 建议媒体文件提前预处理，降低实时转码压力

这部分不是实现细节，而是架构前提。忽略这些约束，软件设计本身也无法保证长期稳定。

## 依赖边界

即使经过重构，系统仍然有不可消除的外部依赖，但它们必须保持边界清晰：

- 推流依赖 `ffmpeg`
- 远端直播依赖斗鱼 RTMP 推流入口
- 弹幕控制依赖斗鱼弹幕通道可用
- 视频库依赖本地存储稳定可读

这些依赖都必须被主程序隔离处理，不允许外部依赖泄漏成到处散落的脚本耦合。

## 非目标

以下内容不属于当前主架构目标：

- 常驻浏览器自动化取码
- 多服务容器编排作为默认主链路
- 本地 relay 中转作为默认主链路
- 数据库存储
- 多用户后台
- 复杂 Web 管理台
- 多平台统一桌面运行体验

这些方向可以后续按需要补充，但不应反向影响树莓派主线架构。

## 文档边界

本文档只描述树莓派 4B 优先的新系统目标架构。

后续实现应以本文档为准，默认主方案为：

- Go 主程序
- `ffmpeg` 直推斗鱼
- 小而明确的弹幕命令集
- 手动配置推流地址和推流码
- 单容器 Docker 部署
